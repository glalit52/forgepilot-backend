# ForgePilot backend

The control plane for [ForgePilot](https://github.com/glalit52/forgepilot-frontend): the API the web app talks to, the closed-loop engine (task → agent → pull request → verification → fix → review → merge → maintenance), background workers, and the connectors to GitHub, Stripe, Slack, Linear, Jira, OSV and coding agents.

It implements every endpoint of the web app's contract (`docs/ui-contract.md`, generated by the frontend) with the same request and response schemas, so the app switches from its mock API to this backend by changing one setting.

## Run it

You need Node.js 22+ and pnpm. No database to install: by default it uses an embedded Postgres stored in `.data/`.

```bash
pnpm install
```

```bash
DEMO_MODE=true pnpm dev
```

The API is at <http://localhost:8080/api/v1>. With `DEMO_MODE=true` it loads the same fictional workspaces the web app was designed against, and agents, test runs and scans are simulated, so every flow works without any external account.

To point the web app at it, start the frontend with `BACKEND_URL=http://localhost:8080 NEXT_PUBLIC_API_BASE=/api/v1`. It proxies API calls through its own address, which matters because the session cookie is `HttpOnly` and `SameSite=Lax`.

With real Postgres, and the API and workers as separate processes:

```bash
docker compose up --build
```

## Checks

| Command                          | What it checks                                                        |
| -------------------------------- | --------------------------------------------------------------------- |
| `pnpm lint` / `pnpm typecheck`   | Code style and strict TypeScript                                      |
| `pnpm test`                      | 111 tests on the embedded database                                    |
| `TEST_DATABASE_URL=… pnpm test`  | The same tests on a real Postgres (pooling, row locks, LISTEN/NOTIFY) |
| `pnpm build`                     | Production bundle in `dist/`                                          |
| `pnpm openapi`                   | Regenerates `docs/openapi.json` from the route tables                 |
| `pnpm contract:sync ../frontend` | Pulls updated schemas, demo data and endpoint list from the web app   |

What the tests cover: every read endpoint against its schema for several personas; that each contract endpoint exists with the same access rule; the closed loop and its guardrails (no auto-merge, capped fix retries, budget hard cap, approvals, honest failure classes); tenant isolation; real sign-up/sign-in, invitations, password reset, API keys, CSRF, idempotency and rate limits; two instances sharing one database; the job queue; and a no-network end-to-end run of live mode (fake GitHub API, a local git remote and a stand-in agent CLI).

## How it is built

```
src/
  contract/      Zod schemas and domain rules, copied verbatim from the web app (single source of truth)
  domain/        route table, closed-loop engine (loop.ts), read models, request engine
  tenancy/       TenantStore: per-workspace unit of work on Postgres
  identity/      users, sessions, API keys, invitations, workspace provisioning, account routes
  execution/     execution plane: agent adapters, sandbox, git, test runner, repository intelligence
  connectors/    GitHub App, Stripe, Slack/Teams/email, Linear/Jira, OSV + registries, customer webhooks
  integrations/  webhook processors (GitHub, Stripe) and event fan-out
  platform/      database, migrations, job queue, change bus, crypto/vault, metrics, rate limits
  http/          Fastify server: auth, CSRF, idempotency, SSE, webhooks, OpenAPI
  demo/          demo seed and reset
```

- **One route table.** Each endpoint declares method, path, permission, request and response schema. The HTTP layer, the OpenAPI document and the contract tests are derived from it. Responses are validated against the schema (a mismatch fails tests and is logged in production).
- **Workspace transactions.** A write loads the workspace, runs the handler on a private draft, and commits exactly the entities that changed, in one Postgres transaction that holds the workspace's row lock. A failed request changes nothing. Changed entities are validated against the contract before they are stored.
- **Jobs are the outbox.** Background work is enqueued in the same transaction as the state change that needs it (`FOR UPDATE SKIP LOCKED` queue, retries with backoff, dedupe keys). Workers are idempotent.
- **Control plane vs execution plane.** The API never runs repository code. Agents and tests run in workers, in a throwaway container per command (`EXECUTION_SANDBOX=docker`), with the workspace as the only mount and no ForgePilot credentials. The git token is passed per command and never written into the clone.
- **Two execution modes.** `simulated` produces outcomes after a short delay (demo, tests, local work). `live` clones, runs the agent CLI, pushes a branch, opens the PR, runs the repository's test commands at the exact commit, posts a GitHub check run, and scans manifests against OSV. Both report through the same lifecycle functions.

### Security

- Sessions are opaque random tokens; only their SHA-256 is stored. Cookies are `HttpOnly`, `SameSite=Lax`, `Secure` in production. Passwords use scrypt.
- Cookie-authenticated writes must be JSON and, when the browser sends `Origin`, come from the web app.
- API keys (`fp_live_…`) are shown once, stored hashed, act as their creator capped at the role they were created with, and stop working when that person leaves.
- Integration credentials are encrypted with AES-256-GCM (`VAULT_KEY`), bound to their workspace, and never returned by the API.
- Webhooks: GitHub and Stripe signatures are verified over the raw body, deliveries are de-duplicated, and a pull request's state is re-read from GitHub rather than trusted from the payload. Merges only ever come from GitHub.
- Customer webhook URLs and connector URLs are restricted to public HTTPS hosts (SSRF guard, re-checked at delivery).
- Logs, diffs and errors are redacted; a change containing a credential that was given to the session is not pushed.

### Three levels of access

- **Workspace (tenant):** one customer's isolated space. Every workspace route only ever sees its own data.
- **Roles inside a workspace:** owner, admin, member, viewer.
- **Staff (super admin):** ForgePilot's own team, listed in `PLATFORM_ADMIN_EMAILS`, using `/admin/*`. They can find, suspend, restore and re-plan workspaces and retry jobs; they cannot read a customer's code, logs or credentials there. Every staff action is audited, and the customer sees suspensions and plan changes in their own audit log.

Staff must also have two-factor sign-in (an authenticator app) turned on. Enterprise workspaces can sign in through their own identity provider (Okta, Microsoft Entra ID) once staff have approved their email domain.

Also enforced: suspended workspaces are read-only; in live mode a plan's concurrent-session limit is a hard stop; each workspace's retention policy is applied daily; owners can delete their workspace and people their account.

### API additions beyond the web app's contract

Real sign-in (`/auth/login`, `/auth/logout`, `/auth/github/start`, `/auth/password/*`), `/me`, invitation acceptance, customer webhooks (`/webhook-endpoints`), the Stripe portal (`/billing/portal`), Linear/Jira import (`/integrations/:providerId/issues`), `/events` (SSE), `/webhooks/github`, `/webhooks/stripe`, `/openapi.json`, plus `/healthz`, `/readyz` and `/metrics`. Errors keep the `{ error, details }` shape and add `code` and `requestId`. POSTs accept an `Idempotency-Key`.

## Known limits

Stated plainly so nobody is surprised later:

- **Not exercised against the real services.** The GitHub, Stripe, Slack, Linear, Jira, OSV and agent-CLI connectors are tested against fakes, not live accounts. Expect small fixes on first contact, the Codex CLI adapter most of all.
- **Workspace data is stored as validated JSON documents** (`tenant_records`), not one typed table per entity as the PRD's data model sketches, and a workspace is held in memory as a whole while it is in use. This is what made exact contract parity practical; it is comfortable for thousands of records per workspace. Test results, usage records and the audit log are the first to move to dedicated tables when a tenant outgrows it. Postgres row-level security is not enabled yet.
- **Rate limits are per process.** Behind several API instances, move the counter to Redis.
- **The egress allowlist is not enforced** in the sandbox (network is on or off); that needs a proxy.
- **Demo mode has passwordless persona sign-in** and must never run with customer data. In production it refuses to start with a real database unless explicitly allowed.
- **The web app side is in [forgepilot-frontend#2](https://github.com/glalit52/forgepilot-frontend/pull/2)**: password sign-up, real sign-in and sign-out, and GitHub App installation. GitHub sign-in and the install redirect still need real GitHub credentials to be tried.
- **The web app has no screens yet for** the email links this backend sends (`/verify-email`, `/reset-password`), for the staff back-office, or for deleting a workspace or account. The endpoints exist and are tested.
- Not built yet: screenshots and traces from browser tests (the file storage for them exists), OpenTelemetry tracing, SCIM user provisioning. Single sign-on uses OpenID Connect, not SAML.

## Configuration

To connect your own accounts (database, GitHub App, Stripe, email, agents), follow [`docs/CONNECTORS.md`](docs/CONNECTORS.md) and check progress with `pnpm run connectors`.

Everything is an environment variable, validated at boot. See [`.env.example`](.env.example). Production requires `VAULT_KEY` and `COOKIE_SECURE=true`; `EXECUTION_MODE=live` requires the GitHub App settings.
